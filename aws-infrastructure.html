AWS Cloud Infrastructure

A small, segmented network on AWS in us-east-1 (North America East). Two public subnets in separate Availability Zones, each with its own route table and a web server. Access is granted by least privilege, and a static website is hosted on S3 with its public access reviewed.

Overview Case study Architecture 1. Network 2. Routing 3. Security groups 4. IAM 5. Servers 6. S3 website Verify Troubleshooting Lessons learned Cleanup

Overview

The goal was a repeatable environment where every resource has one job and only the traffic it needs is allowed.

  • Network: one VPC, two public subnets in two Availability Zones, and an internet gateway.
  • Routing: two route tables, one per subnet.
  • Security: three security groups, one per job: admin, web, and internal.
  • Access: two users, one group, two roles, and four policies.
  • Compute: two Linux servers, managed over SSH and Systems Manager.
  • Website: a static site on S3, with public access limited to reading the site files.

The problem this solves

Many small offices run their internal app on a single computer that is reachable from the internet. Everyone shares one administrator login, and the public information page sits on a hosting service that the team can't easily lock down. One lost password can lock out the whole office.

What this design does

  • Runs the app on servers that accept connections only from the places they need.
  • Gives each person only the access their role requires.
  • Hosts the public page where visitors can read it but can't change it.

Step 1: Build the network

  1. Create the VPC. In the VPC console for us-east-1, choose VPC only, name it webapp-vpc, and set the IPv4 CIDR to 10.0.0.0/16.
  2. Create two public subnets in two Availability Zones: webapp-public-a in the first zone with 10.0.0.0/24, and webapp-public-b in the second zone with 10.0.1.0/24.
  3. Turn on auto-assign public IPv4 for both subnets (Actions → Edit subnet settings), so each server gets a public address.
  4. Create and attach an internet gateway named webapp-igw to webapp-vpc.

Why two Availability Zones? If one zone has an outage, the other subnet and its server keep running.

Step 2: Set up two route tables

Each public subnet gets its own route table. Both send internet traffic to the same gateway, so either subnet can serve visitors even if the other is down.

  1. Rename the VPC's default route table to webapp-public-rt-a. It starts with only the local route.
  2. Add the internet route: Routes → Edit routes → Add route, destination 0.0.0.0/0, target webapp-igw.
  3. Associate it with webapp-public-a (Subnet associations → Edit subnet associations).
  4. Create webapp-public-rt-b in the same VPC, add the same 0.0.0.0/0 route to webapp-igw, and associate it with webapp-public-b.
Route tableDestinationTargetSubnet
webapp-public-rt-a10.0.0.0/16localwebapp-public-a
webapp-public-rt-a0.0.0.0/0webapp-igwwebapp-public-a
webapp-public-rt-b10.0.0.0/16localwebapp-public-b
webapp-public-rt-b0.0.0.0/0webapp-igwwebapp-public-b

A subnet is "public" only when its route table has a 0.0.0.0/0 route to an internet gateway. The subnet setting alone is not enough.

Step 3: Create three security groups

Each group has one purpose, so every rule has a clear reason:

GroupPurposeInbound rules
webapp-admin-sgRemote administrationSSH (TCP 22) from my IP address only
webapp-web-sgWeb trafficHTTP (TCP 80) from 0.0.0.0/0
webapp-internal-sgTraffic between the two serversAll TCP from webapp-internal-sg itself

Outbound rules stay at the default (all outbound allowed), so the servers can install updates. AWS warns when a rule allows 0.0.0.0/0. That's expected for the web group, but SSH must never be open to everyone.

Step 4: Grant access with IAM

The access model uses the least privilege each identity needs:

NameTypePurpose
ops-adminUserBuilds and manages the project
dev-engineerUserWorks only on development servers, through developers
developersGroupHolds the developer-ec2-policy policy
ec2-ssm-roleRoleAttached to the servers, so Systems Manager can manage them without open SSH
ops-monitoring-roleRoleRead-only checks for the website and server inventory, used by ops-admin

The four policies

  1. developer-ec2-policy (attached to developers): lets the developer manage EC2 instances only when the instance has the tag Env=development, and denies changes to tags on any instance.
  2. ec2-read-only-policy (attached to ops-monitoring-role): lets the role list EC2 instances.
  3. ssm-access-policy (attached to ec2-ssm-role): lets the servers connect to Systems Manager.
  4. website-read-policy (attached to ops-monitoring-role): lets the role read the website files in the bucket, and nothing else.

The developer policy is the most important one. It allows all EC2 actions only on development instances, and the explicit deny stops any change to tags:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ManageDevelopmentOnly",
      "Effect": "Allow",
      "Action": "ec2:*",
      "Resource": "*",
      "Condition": { "StringEquals": { "ec2:ResourceTag/Env": "development" } }
    },
    {
      "Sid": "NoTagChanges",
      "Effect": "Deny",
      "Action": ["ec2:CreateTags", "ec2:DeleteTags"],
      "Resource": "*"
    }
  ]
}

A deny always overrides an allow. Turn on multi-factor authentication for both users, and never use the root account for daily work.

Step 5: Launch two EC2 servers

  1. Launch webapp-web-01: Amazon Linux 2023, t2.micro, in webapp-public-a. Create a key pair named webapp-keypair and keep the .pem file safe.
  2. Attach security groups: webapp-admin-sg, webapp-web-sg, and webapp-internal-sg.
  3. Tag it Env=development, so the developer policy applies.
  4. Launch webapp-web-02 the same way, in webapp-public-b.
  5. Attach ec2-ssm-role to both servers as the instance profile.

Connect from your computer, then check the server:

# Replace the public IP with the server's address
chmod 400 webapp-keypair.pem
ssh -i webapp-keypair.pem ec2-user@<public-ip>

uname -a
systemctl status sshd
df -h

For everyday administration, use Systems Manager Session Manager. It needs no open SSH port, and every session is logged.

Step 6: Host the website on S3

The site is hosted from a bucket, not from the servers, so it stays up even if a server is stopped. Public access is limited to reading the site files:

  1. Create the bucket webapp-site-[yourname] in us-east-1. Bucket names are unique worldwide.
  2. Upload index.html and its images.
  3. Enable static website hosting in Properties, with index.html as the index document.
  4. Limit public access. Keep all four Block Public Access settings on, except Block public access to buckets and objects granted through new public bucket policies. Then add a policy that allows only reading the site's files:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicReadSiteFiles",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::webapp-site-yourname/*"
  }]
}

This keeps the bucket private by default and opens only one action, GetObject, for the site's files. Visitors can't list, write, or delete anything.

Check the settings after every change. If a new policy grants more than s3:GetObject, remove it.

Verify

  • SSH to each server works from your IP address, and is refused from anywhere else.
  • The website loads from the bucket's website endpoint, and anonymous uploads are refused.
  • The two servers can reach each other over webapp-internal-sg.
  • dev-engineer can see and stop instances tagged Env=development, and can't change any tags.

Troubleshooting

SymptomLikely causeFix
SSH times outYour IP isn't in webapp-admin-sg, or the server has no public IPUpdate the admin rule and check auto-assign on the subnet
Website shows 403 ForbiddenThe bucket policy is missing, or a Block Public Access setting still blocks itReview the policy and the four settings
Servers can't update packagesThe subnet's route table has no 0.0.0.0/0 routeCheck both route tables and their subnet associations
Developer gets "not authorized"The instance is missing the Env=development tagAdd the tag, or check the policy condition

Lessons learned

Building a network like this usually runs into the same few problems. Here is what they look like, why they happen, and how to fix them.

What goes wrongWhy it happensHow to fix it
A server is "public" but the website won't loadThe subnet has a public IP setting, but its route table never got an internet routeOpen the subnet's route table and confirm it sends 0.0.0.0/0 to the internet gateway. Give each route table a name that matches its subnet.
You suddenly can't connect over SSHHome internet providers change your public IP address from time to time, so the admin rule no longer matches youUpdate the admin rule to your current IP. For a long-term setup, use Systems Manager Session Manager instead of SSH.
SSH refuses the key with an UNPROTECTED PRIVATE KEY FILE warningThe key file can be read by other users on your computer, and SSH refuses to trust itRun chmod 400 on the key file so only you can read it.
An IAM policy won't saveThere is a typo in the JSON, such as a missing comma or quotation markPaste the policy into the IAM policy editor. It points to the line with the error.
The website bucket name is already takenBucket names must be unique across all of AWS, not just your own accountAdd your name or a project code to the bucket name.
A developer can't stop a serverThe server doesn't have the Env=development tag, so the developer policy doesn't apply to itAdd the tag to the server. Tag every server when you launch it so this doesn't happen.
The AWS bill is higher than expectedServers were left running after testingStop or terminate servers when you're finished. Set a billing alarm in the Billing console so you get warned early.
Servers can't install updatesThe route table has no internet route, or the network ACL blocks outgoing trafficCheck the internet route first, then check the network ACL's outbound rules.

Cleanup

To avoid charges: terminate both servers, empty and delete the website bucket, then remove the users, group, roles, and policies. Next, detach and delete webapp-igw, delete both route tables, the security groups, the subnets, and finally the VPC.
