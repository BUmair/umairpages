AWS Serverless Automation

A file-processing workflow in us-east-1 (North America East). Uploading a file to S3 triggers a Lambda function directly, so no server waits for files and no compute runs while the bucket is idle. CloudWatch records every run.

Overview Case study Architecture 1. Buckets 2. Event notifications 3. Functions 4. Permissions 5. Testing 6. CloudWatch Troubleshooting Lessons learned Cleanup

Overview

Uploads used to be handled by hand. This workflow handles them automatically and stays secure by default:

  • Three event notifications, each matching one kind of upload by its folder and file type.
  • Three Lambda functions, each handling one kind of upload.
  • No polling. S3 calls the function when a file arrives, which reduces idle compute cost.
  • Least privilege. Each function can read only its own input and write only to the output folder.
  • Monitoring. CloudWatch logs and alarms show each run and any failure.

The problem this solves

Small bookkeeping and admin teams often receive files in several formats every day, such as bank statements, accounting exports, and scanned receipts. Someone downloads each file, sorts it by type, and renames it before filing. This takes a lot of time, and files are sometimes misfiled.

What this design does

  • Processes each file automatically as soon as it arrives.
  • Puts all processed results in one folder that staff can review.
  • Charges only for processing that actually happens.

Architecture

Read the diagram in numbered order. An upload lands in the input bucket. S3 checks its folder and file type, then calls the matching function. The function writes the result to the output bucket, and CloudWatch records the run.

Step 1: Create the buckets

  1. Create the input bucket documents-intake-[yourname] in us-east-1, with the default settings (Block Public Access on).
  2. Create the output bucket documents-processed-[yourname] the same way.

Keep the output bucket separate from the input bucket. If results were written back to the input bucket, they could trigger the functions again.

Back to top ↑

Step 2: Create three event notifications

On the input bucket, go to Properties → Event notifications → Create event notification. Create three rules, each with the event type All object create events. Each rule matches a different folder and file type, so every upload triggers exactly one function:

NotificationPrefix (folder)Suffix (file type)Function
csv-uploadeduploads/.csvcsv-processor
json-uploadeduploads/.jsonjson-processor
image-uploadedincoming/.pngimage-processor

Keep prefixes and suffixes unique. S3 rejects two notifications with the same prefix and suffix on the same event type.

Step 3: Create the three functions

  1. Create csv-processor, json-processor, and image-processor with the Python 3.12 runtime. Choose Author from scratch and let Lambda create an execution role for each. Step 4 narrows those roles.
  2. Add the handler code to each function. This version reads the uploaded file and writes a copy to the output bucket:
import json
import urllib.parse
import boto3

s3 = boto3.client("s3")
OUTPUT_BUCKET = "documents-processed-yourname"

def lambda_handler(event, context):
    processed = []
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = urllib.parse.unquote_plus(record["s3"]["object"]["key"])

        body = s3.get_object(Bucket=bucket, Key=key)["Body"].read()

        output_key = "processed/" + key.split("/")[-1]
        s3.put_object(Bucket=OUTPUT_BUCKET, Key=output_key, Body=body)

        print(json.dumps({"input": key, "output": output_key, "bytes": len(body)}))
        processed.append(output_key)

    return {"processed": processed}
  1. Deploy each function. Set a timeout and memory that suit the work, such as 30 seconds and 256 MB for small files. Raise them only if the logs show the function running out of time or memory.

The three functions share this starter code. Replace the middle step in each one for its file type, such as parsing CSV rows, reading JSON fields, or resizing images.

Step 4: Set least-privilege permissions

Each execution role allows only the actions its function uses. Here is csv-processor's role. The other two follow the same pattern, changing the folder and file type:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOwnUploads",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::documents-intake-yourname/uploads/*.csv"
    },
    {
      "Sid": "WriteProcessedOnly",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::documents-processed-yourname/processed/*"
    },
    {
      "Sid": "WriteLogs",
      "Effect": "Allow",
      "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "*"
    }
  ]
}

Keep resource ARNs specific. Avoid s3:* and "Resource": "*" on any data action.

Step 6: Monitor with CloudWatch

  • After each test, open the log group /aws/lambda/csv-processor (and the matching group for each function) and read the newest log stream.
  • Create a CloudWatch alarm on each function's Errors metric, so failures show up without checking logs by hand.
  • Use the Invocations metric to confirm each function runs only when its file type arrives.

Troubleshooting

SymptomLikely causeFix
Function never runsThe folder or file type doesn't match the notificationCompare the key with each notification's prefix and suffix
AccessDenied in logsThe execution role is missing a permissionCheck the role's policy against the bucket and folder
Function runs repeatedlyOutput is written to the input folderWrite only to the output bucket's processed/ folder
Timeout errorsThe file is larger than the timeout allowsRaise the timeout, or split the file

Lessons learned

Event-driven pipelines like this one tend to fail in the same few ways. Here is what to look for, why it happens, and how to fix it.

What goes wrongWhy it happensHow to fix it
A function doesn't run for a .CSV fileThe file extension must match exactly, including capital lettersUpload files with lowercase extensions, or add a separate rule for each capitalization.
A function runs over and overThe function writes its output back into the folder that triggers it, which starts a new run each timeWrite results only to the output bucket. Make sure no rule's folder matches where the output is written.
S3 refuses to save a new event ruleTwo rules use the same folder and file type, so S3 can't tell which one should runChange the folder or file type so each rule is unique.
The logs show AccessDeniedThe function's permissions point to a different folder or bucket name than the one it's usingCompare the bucket and folder names in the role's policy with the names in your code, letter by letter.
Large files stop partway throughThe function's time limit is too short for the fileRaise the timeout. Giving the function more memory also gives it more processing power, which can speed it up.
The same file gets processed twiceS3 can send the same event more than onceWrite output under a fixed name, so a second run replaces the first result instead of creating a duplicate.
No logs appear after an uploadThe function hasn't run yet, or its role is missing permission to write logsUpload a test file, then check that the role can create log groups and write log events.
A test upload does nothing right after setupS3 can take a short time to start using a new event ruleWait a minute and upload again. Confirm the rule appears under the bucket's event notifications.

Cleanup

Remove the three event notifications, delete the three functions and their log groups, then empty and delete both buckets and the execution roles.
