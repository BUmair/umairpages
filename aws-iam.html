AWS IAM Access Control

Outcome: a developer can stop development EC2 instances but cannot touch production ones. The rule is set by a tag, and a separate user login confirms it works.

Overview Decisions Architecture Checks Watch-outs What's next

What I built

Two EC2 instances, one tagged for production and one for development. A JSON policy allows EC2 actions only on instances tagged Env=development, and an explicit deny blocks tag changes. The policy is attached to a user group, and a new developer user joins that group. An account alias gives the sign-in page a readable URL.

Decisions

  • Access by tag, not by instance ID. The condition matches Env=development, so any new development instance is covered as soon as it is tagged.
  • An explicit deny on tag changes. ec2:CreateTags and ec2:DeleteTags are denied, so a developer can't remove or change a tag to get around the rule.
  • Permissions through a group. The policy is attached to dev-group, and users inherit it by membership. Adding the next developer takes one step.
  • Read access everywhere. ec2:Describe* is allowed on all resources, so the developer can see what is running, including production, without being able to change it.
  • Account alias for sign-in. A readable alias replaces the 12-digit account ID in the sign-in URL.

The policy. It has one allow for development instances, one allow for read-only describe calls, and one deny for tag changes:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "ec2:ResourceTag/Env": "development"
        }
      }
    },
    {
      "Effect": "Allow",
      "Action": "ec2:Describe*",
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": [
        "ec2:DeleteTags",
        "ec2:CreateTags"
      ],
      "Resource": "*"
    }
  ]
}

Checks

These are the checks that confirm the policy does what it is meant to do. Each one is run while signed in as the developer user, in a separate incognito window.

#Action as developerExpected result
1Stop the development instanceSucceeds
2Stop the production instanceRefused with an authorization error
3Add or remove a tag on any instanceRefused by the explicit deny
4List instances in the consoleBoth instances are visible

Watch-outs

  • The sign-in URL used an old account alias. The group policy and the user were set up under a new alias, but the account still had an older alias, so the sign-in link did not match what I expected. Check the current alias in the IAM dashboard before sharing the sign-in URL.
  • An instance without the tag gets no development access. The condition checks the tag, so an untagged instance is treated as production. Tag every instance when it is launched.
  • Skipping the key pair and forced password change is for practice only. Both steps are fine for a lab, but a real environment should use a key pair and require a password change on first sign-in.
  • Leftover resources cost money. Delete both instances, the group, the user, the policy, and the account alias when finished.
